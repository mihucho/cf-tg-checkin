# cf-tg-checkin · 整体设计评审与优化方案

评审对象：当前 0.4.7（5 个 tab：概览 / 任务 / 日志 / 账号 / 设置）
评审视角：产品设计（信息架构、核心链路、状态表达、可观测性），不含视觉细化。
结论一句话：**功能已经够用，问题在"第一次能不能跑通"和"失败之后能不能自己修"**。

---

## 1. 用户与核心链路

| 角色 | 核心诉求 | 现在需要走几步 |
| --- | --- | --- |
| 新用户（自己的账号签个到） | 10 分钟内签上第一次到 | 登录页 → 账号三步 → 收藏夹发指令 → 等 1 分钟 → 翻日志 → 改指令 → 再试 |
| 回访用户 | 确认今天签到了 / 某任务为什么挂了 | 概览 → 任务 → 步骤日志（弹窗）→ 日志页（另一处） |
| 调参用户 | 改时间、改按钮、改等待 | 任务编辑器（另一套表单）↔ 指令（又一套语法） |

核心链路本身是对的（登录 → 建任务 → 定时执行 → 日志），**断点在两端**：入口的引导、出口的修复闭环。

---

## 2. 发现的问题（按影响排序）

### P0-1 首屏没有"下一步"
概览只有 4 张状态卡 + 最近活动 + 指令卡片。新用户看到"未登录 / 0 任务 / 还没执行记录"，**没有任何指引**。
账号页有三步向导，但它不在首屏链路上。

**方案**：概览顶部加一条「快速开始」清单（3 步，随状态自动打勾并消失）：
1. 登录 Telegram（未登录时高亮，直接跳账号页）
2. 创建第一个任务（跳任务页 / 或复制示例指令）
3. 发一条测试指令（显示 `tg 9.30 签到` 与"复制"按钮）
三步全部完成后整条收起，不再占位。

### P0-2 任务详情"散落在三个地方"
- 列表行只有摘要与「步骤日志」弹窗（`task.lastDetail`）
- 完整历史在日志页（全局列表，需要按任务筛选）
- 修改在编辑器抽屉

排查一个失败任务要跨 3 个界面、2 种容器（弹窗 + 抽屉 + 页面）。

**方案**：任务行点击 → **右侧详情抽屉**（与编辑器同一容器形态），内含：
- 顶部：状态 / 目标 / 调度 / 下次执行 / 「立即执行」
- 「最近 5 次运行」列表（失败项展开即步骤日志，不弹窗）
- 「查看全部日志」按钮（带 `?taskId=` 跳到日志页）
- 「编辑」按钮切到编辑态（同一抽屉内）

### P0-3 错误信息没有"修复动作"
现状：`还没登录 Telegram`、`触发器轮询失败（控制会话 self）：…`、`未匹配到关键词（签到成功）`。
用户知道错了，但不知道点哪里。日志里也没有"来源"（自动 / 手动 / 指令），排查连发时缺关键信息。

**方案**：
- 日志/步骤日志里给每条错误配一个动作：
  - 未登录 → 「去登录」
  - 找不到目标 → 「编辑目标」
  - 未匹配关键词 → 「查看原始回复」（展开消息文本）+ 「调整关键词」
  - 连接类 → 「重试」+ 说明"会自动重连"
- 日志行加两个 badge：**来源**（自动 / 手动 / 指令）、**耗时**（如 1.8s）

### P0-4 连接状态语义过载
现在有 `signedIn`（有 session）、`connected`（活跃 socket）、`lastConnectedAt`，界面上表现为"未登录 / 已连接 / 空闲"，
用户最关心的问题其实是：**"它现在能不能替我干活？"**

**方案**：收敛成一个主状态 + 一句补充：
```
Telegram  ✓ 已登录 @xxx · 上次通信 2 分钟前
          定时任务照常执行，需要时才连接
```
只有"未登录"是异常态，其余都不该让用户紧张。

### P1-1 两套建任务方式没有互相映射（差异化没被用起来）
产品最有辨识度的能力是"消息即配置"，但界面上：编辑器是一套、指令是另一套，用户不知道两者等价。

**方案**：
- 编辑器底部显示："等价指令：`tg 9.30 /start btn:签到 #kw:签到成功`" + 「复制」
- 指令试算结果加「用这条指令建任务」按钮（当前只能预览）
- 任务详情抽屉里加「复制为指令」（备份 / 分享用）

### P1-2 失败无人通知
签到失败只在日志里。用户不会天天开后台，等于"静默失败"。

**方案**：设置里加「失败通知」：
- Telegram 私聊自己（用当前登录账号给自己发一条，零成本）
- 或 Webhook（自定义 URL，可选）
- 节流：同一任务 1 小时内最多 1 条

### P1-3 没有熔断
刚刚真实发生过：一个窗口任务连发 9 次。即使调度修好了，也需要"连续失败/异常频次"的保护。

**方案**：同一任务同一天执行 ≥2 次（非 interval）或连续失败 ≥3 次 → **自动暂停** + 概览标红 + 一条明确日志
（"已自动暂停：检测到重复执行，请检查指令"）。

### P2（下一轮再做）
- 模板库（两级菜单签到 / 随机问候 / 每日打卡）一键创建
- 一个任务多目标（批量）
- 设置页按「执行 / 消息指令 / 登录与安全 / 关于」重组（现在是把实现字段平铺）
- 移动端 375px 细化（设置长表单、日志筛选行折行顺序）
- 键盘可达性：tab 的 `aria-current`、日志行展开、抽屉关闭后的焦点还原

## 3. 优先排序

| 优先级 | 事项 | 影响 | 工作量 |
| --- | --- | --- | --- |
| P0-1 | 概览「快速开始」清单 | 首次成功率 | 0.5 天 |
| P0-2 | 任务详情抽屉（合并三处信息） | 排查效率 | 1 天 |
| P0-3 | 错误 → 修复动作 + 日志来源/耗时 | 自助修复 | 0.5 天 |
| P0-4 | 连接状态收敛成一句话 | 理解成本 | 0.2 天 |
| P1-1 | 指令 ⇄ 编辑器互转 + 复制 | 差异化、留存 | 0.5 天 |
| P1-2 | 失败通知（Telegram 私聊 / Webhook） | 静默失败 | 0.5 天 |
| P1-3 | 重复执行 / 连续失败自动暂停 | 稳定性体感 | 0.3 天 |

建议节奏：**P0 一轮做完**（约 2 天），再做 P1-1 与 P1-3（约 1 天），P1-2 视需求。

## 4. 验收与指标

| 指标 | 现状（估） | 目标 |
| --- | --- | --- |
| 首次成功签到耗时（登录→第一条成功日志） | 未知，链路 6+ 步 | 中位数 ≤ 10 分钟 |
| 指令建任务占比 | 未知 | ≥ 40%（说明差异化生效） |
| 任务 7 日存活率 | 未知 | ≥ 70% |
| 失败后是否处理（打开详情 / 编辑 / 重试） | 无埋点 | ≥ 50% |

> 现在没有埋点。P0 落地时顺手加最小事件（`first_login`、`task_created`、`run_failed`、`failure_handled`），
> 只计数、不采内容，存在 DO 里即可。

---

## 5. 不做的事

- 不做多用户/权限体系（单管理员是产品定位）
- 不做可视化流程编排（指令 + 结构化表单已够）
- 不做移动端独立 App（响应式够用）
